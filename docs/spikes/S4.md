# S4: Google OAuth client for the claim app

Status: **waiting on the owner** to create the client. The verifier side is done:
`verifier/src/googleIdToken.ts` checks a token with the nonce rule, and its tests use a
self-signed JWKS (no Google account needed).

Facts below were read from Google's docs on 2026-11-10 (links at the end).

## What the owner creates (Google Cloud Console)

1. **Google Auth Platform → Branding / Audience** (the OAuth consent screen)
   - User type: **External**. App name: "Zarf on NEAR". Support email: the owner's.
   - Scopes: **`openid`, `email`** only. Both are non-sensitive.
   - Publishing status: **In production**. Google says apps that ask only for
     `openid`/`email`/`profile` don't need a test-user list, show no warning, and
     their sign-ins don't expire after 7 days. That matters because judges sign in with
     their own Gmail. Inferred, not stated: with only these scopes, no verification
     review and no "unverified app" screen.
2. **Clients → Create client → Web application**, name `zarf-near-claim`.
   - **Authorized JavaScript origins**
     - `http://localhost` and `http://localhost:5173` (Google asks for both forms on localhost)
     - `https://<claim-host>` (the testnet claim app, see below)
   - **Authorized redirect URIs** (exact match: scheme, host, port, path, trailing `/`)
     - `http://localhost:5173/auth/google`
     - `https://<claim-host>/auth/google`
3. Send the **client id** to `zarf main`. It is public (it ships in the page). There is
   **no client secret** in this flow: don't create or share one.

`<claim-host>` must be decided first. Wildcards and raw IPs are not allowed, and only
localhost may use plain `http`. A `*.workers.dev` or `*.pages.dev` host works. Adding a
host later is fine, but Google says changes can take 5 minutes to a few hours to apply.

The verifier's `GOOGLE_CLIENT_ID` var (`verifier/wrangler.jsonc`) must be set to the same id.
Until then the verifier rejects every request (it fails closed when the var is empty).

## Passing our nonce

The nonce is `lowercase_hex(sha256(utf8(destination)))` (`spec/claim.md`). The claim app
computes it **before** sign-in, after the recipient has picked a destination.

| | OAuth redirect (`response_type=id_token`) | Google Identity Services (GIS) button |
| --- | --- | --- |
| How the nonce goes in | `nonce=<hex>` query parameter on `https://accounts.google.com/o/oauth2/v2/auth` | `google.accounts.id.initialize({ client_id, nonce, callback })` |
| Where the token comes back | URL fragment of the redirect URI (`#id_token=…&state=…`) | JS callback (`credential`) |
| Console config | redirect URI + origin | origin only |
| Phones / in-app browsers | full-page redirect, nothing to block | popup or FedCM; One Tap needs HTTPS |
| Prior use | Zarf on Stellar uses this today (`web/packages/ui/lib/utils/googleAuth.ts`, mainnet claims) | not used by us |

**Recommendation: the redirect flow.** We already run it in production with a custom
nonce. It has no popups and no third-party cookie or FedCM issues. It also works the same
in the phone browsers that judges open from a link. Its one dependency is a fixed redirect path
(`/auth/google`). The claim link's campaign id and commitment ride in `state` and are
restored after the redirect.

Request: `client_id`, `redirect_uri`, `response_type=id_token`, `scope=openid email`,
`nonce=<hex>`, `state=<campaign/commitment>`, `prompt=select_account`.

Google calls the implicit flow insecure for SPAs because the token sits in the URL
fragment. Our token can only be used once: it is bound to one destination through the
nonce and expires within an hour. Even so, the claim page should:

- clear the fragment at once (`history.replaceState`);
- load no third-party scripts;
- send `Referrer-Policy: no-referrer`;
- send the token only to the verifier.

# Claim format (v2.1)

Every layer — `contract/` (Rust), `verifier/`, `faucet/` and `web/` (TypeScript) — must
agree on these bytes exactly. `spec/vectors.json` is generated by `spec/gen-vectors.mjs`
and is the acceptance test. Every layer's suite loads it, **asserts the vector counts are
non-zero**, and reproduces every value. Change this file only together with the generator,
then regenerate.

Owner: orchestrator (`zarf main`). Other sessions propose changes; they don't edit.

v2 changes from v1: per-recipient salt in the claim link (nothing is sealed); verifier
registry inside the escrow (Mode W owner keys, Mode T attested Shade agents); `network` as
an init arg; events, views, check order and deadline boundary defined; ASCII-only emails.

## Encodings

- Bytes in JSON: lowercase hex, no `0x`.
- `u64` / `u128` in JSON: decimal strings (NEAR `U64`/`U128`).
- Integers inside hashed or signed bytes: little-endian, fixed width.
- Strings inside hashed or signed bytes: ASCII/UTF-8 with a 1-byte length prefix
  (account ids are ≤ 64 bytes).
- All times are **nanoseconds** (`env::block_timestamp()`), named `*_ns`.

## Email, salt, commitment

```
canonical_email = lowercase(trim(email))   // ASCII only: after trim and BEFORE lowercasing, every byte is 0x21..0x7e, else refused
salt_i          = 32 random bytes, one per recipient (never reused, never on chain)
commitment_i    = HMAC-SHA256(key = salt_i, msg = canonical_email)      // 32 bytes
```

- `trim` removes only ASCII space, tab, CR and LF. The create app refuses any address that
  is not ASCII after trimming, including a CSV BOM. No dot/plus folding: the CSV must hold
  the address Google returns in `email`.
- The same email may appear twice. Different salts give different commitments, so each row
  is a separate allocation.
- **The claim link carries the salt in the fragment:**
  `https://<claim-host>/claim/<campaign_id>/<commitment>#s=<salt_hex>`.
  The fragment never reaches a server. The claim app sends `salt` only in the POST to the
  verifier, together with the id_token. The claim app removes the fragment with
  `history.replaceState` right after reading it, and the verifier never logs `salt`.

A leaked link lets its holder test one guessed email against one commitment; it does not
let anyone claim without that Google account.

## Merkle tree

```
leaf = sha256(0x00 || commitment[32] || amount_u128_le[16])
node = sha256(0x01 || min(a, b) || max(a, b))      // byte-wise lexicographic order
```

- A tree has **at least one leaf**. Leaves are in CSV order. On a level with an odd count the
  last node is **carried up unchanged** (never duplicated). One leaf: `root = leaf`,
  `proof = []` (the contract must accept an empty proof).
- `proof` = sibling hashes from leaf to root, skipping the levels where the node was carried up.
- Verify: `h = leaf; for s in proof: h = node(h, s); h == root`.
- `proof.len() <= 20`, else `E108_INVALID_INPUT`.
- `amount == 0` is refused: the create app never builds such a leaf, and `claim` returns
  `E109_INVALID_AMOUNT`.

## Nonce (Google `nonce` claim)

```
nonce = lowercase_hex(sha256(destination))     // 64 chars
```

`destination` is the NEAR account the contract pays: the recipient's account or the 1Click
deposit address. It must parse as a valid NEAR `AccountId`, and the claim app and the
verifier both check that **before** the nonce is computed or anything is signed. It is
chosen before the Google redirect.

## Signed claim payload

```
payload =
    "ZARF-NEAR-CLAIM-V1"                  // 18 ASCII bytes, domain tag
 || u8 len || network                     // "testnet" | "mainnet"
 || u8 len || contract_id
 || u64_le(campaign_id)
 || commitment[32]
 || u128_le(amount)
 || u8 len || destination
 || u64_le(expires_at_ns)
signature = ed25519_sign(signer_priv, payload)        // over the raw payload bytes
```

- `network` is an **immutable init arg** of the contract, exposed by `get_network()`. The
  verifier reads it from that view; it never derives it from an account suffix.
- `contract_id` is `env::current_account_id()` on chain; the verifier gets it from its config.
- **Every layer rebuilds `payload` from the call args plus its own context and verifies
  that.** None passes a received payload to ed25519 directly. The vectors' `payload` field
  exists only to compare against the rebuilt one.
- The verifier sets `expires_at_ns = now + 10 min`. The contract refuses
  `expires_at_ns < now` (`E114_CLAIM_EXPIRED`) and `expires_at_ns > now + 1 h`
  (`E108_INVALID_INPUT`).

## Verifier registry (in the escrow)

The signer is identified by `signer`, the hex of its 32-byte ed25519 public key. For a Shade
agent this is also its implicit account id.

```
agents: signer -> { kind: Owner | Attested { measurement_id }, valid_until_ns }
```

- **Mode W:** the owner calls `add_owner_key({ signer, valid_until_ns })` and `remove_agent({ account_id })`
  (`account_id` = the signer hex, matching the Shade template's argument name).
  `add_owner_key` on a signer that already exists (of either kind) is refused with
  `E108_INVALID_INPUT`. An entry never changes kind. To extend a key, call `remove_agent`
  and `add_owner_key` in **one batched transaction**: a gap between them freezes that key's
  campaigns.
- **Mode T:** these methods keep the Shade CLI's argument shapes, so `shade deploy` drives them unchanged.
  - `approve_measurements({ measurements })` / `remove_measurements`, owner only.
  - `approve_ppids({ ppids })` / `remove_ppids`, owner only.
  - `register_agent({ attestation })`, payable. Called by the agent; it runs
    `shade_attestation::verify` with `report_data` = the caller's account id, and stores
    `Attested { measurement_id }` with `valid_until_ns = now + agent_ttl_ns`
    (`agent_ttl_ns` is an init arg: 7 days, the CLI's re-registration period).
    The first registration attaches 0.005 NEAR, so storage must cost ≤ 0.005 NEAR. A
    refresh by an agent that is already registered attaches **0** and must not be charged.
    Returns `true`, since the Shade client treats a falsy result as failure.
  - `get_agent({ account_id })`, a view.
- **One id per measurement:**
  `measurement_id = sha256(canonical_json(measurement))`. `measurement` is a single
  `FullMeasurementsHex` object as `approve_measurements` receives it (field set from
  `shade-attestation 0.2.0`). `canonical_json` means keys sorted byte-wise at every depth,
  no whitespace, UTF-8. Every hex string is lowercase: `approve_measurements` refuses any
  uppercase hex with `E108_INVALID_INPUT` rather than normalising it. `approve_measurements` stores each
  measurement under its own id, so approving or removing one never changes another's id.
  Vector: `measurement_id` in vectors.json.

**Campaign policy snapshot.** `msg.policy` chooses the policy at creation, and the contract stores it:

- `"owner"`: the Owner signers with `valid_until_ns >= deadline_ns`. A key that expires
  before the deadline is left out, so the campaign can't freeze mid-life.
- `"attested"`: the set of `measurement_id`s approved at creation time.

A later `add_owner_key` or `approve_measurements` does **not** extend an existing campaign.
A re-registered agent (new key after a TEE reboot) with an approved measurement in the
snapshot is accepted. An empty snapshot fails creation with `E127_NO_VERIFIER` (refunded).

Trust-model consequences, to be stated in the README:

- `remove_agent` on a snapshotted owner key freezes that campaign's claims until `reclaim`.
  Revocation therefore costs liveness, never funds.
- ppids are **not** snapshotted. A later `approve_ppids` lets new hardware running the
  same approved code register agents for existing attested campaigns.
- `remove_measurements` stops new registrations only. It neither revokes existing agents
  nor touches snapshots; `remove_agent` is the only lever for those.

`claim` accepts `signature` only if `agents[signer]` exists, `valid_until_ns >= now`, and
`signer` (owner) or its `measurement_id` (attested) is in the campaign snapshot; otherwise
`E101_INVALID_SIGNATURE`. Then `env::ed25519_verify(signature, payload, signer)`.

## Contract calls (JSON args)

`new({ owner_id, network, token_ids, min_lifetime_ns, agent_ttl_ns })`. `network` and
`min_lifetime_ns` are immutable. `min_lifetime_ns` = 600 s on testnet and 30 days on mainnet.
`ft_storage_deposit` is read from each allowed token's `storage_balance_bounds().min` when
the token is allow-listed, and stored (USDC: 0.00125 NEAR).

`ft_on_transfer(sender_id, amount, msg)`, where `msg` is

```json
{ "merkle_root": "<hex32>", "deadline_ns": "<u64>", "policy": "owner" | "attested", "leaf_count": <u32> }
```

Any error panics, so NEP-141 refunds the whole amount. On success it returns `"0"`.

**`(sender_id, merkle_root)` is an idempotency key.** A campaign from the same NEP-141
`sender_id` with the same root is refused with `E132_DUPLICATE_CAMPAIGN` (refunded). Each
draft has fresh random salts, so a repeat can only be a resend of the same draft, and a
draft can never be funded twice whatever the app does. The key includes the sender, so
nobody else can occupy a sender's root by front-running it. The view
`campaign_by_root({ sender, merkle_root })` → `"<u64>" | null` exposes the mapping. The
probe in `new` measures this entry, and its cost is included in `campaign_bytes_cost`. The create app persists `{ draft, sender }` **before** calling the wallet. After a
wallet error or a reload, it never says "nothing was sent": it checks
`campaign_by_root({ sender, merkle_root })`, and only if that is null does it allow Create
again.

`claim`:

```json
{ "campaign_id": "<u64>", "commitment": "<hex32>", "amount": "<u128>", "proof": ["<hex32>"],
  "destination": "<account_id>", "expires_at_ns": "<u64>", "signer": "<hex32>", "signature": "<hex64>" }
```

`reclaim({ campaign_id })`: sender only.

`resolve_pending({ campaign_id, commitment, paid, evidence })`, owner only. It is the exit
for a claim stranded in `pending` because its callback never completed (out of gas, panic).

- Allowed only when the pending entry is older than 1 h (`started_ns` is stored with it); else
  `E107_UNAUTHORIZED`.
- `paid: true` → `claimed` and the amount leaves in-flight. `paid: false` → `unclaimed` and
  in-flight moves back to balance.
- `evidence` is the `ft_transfer` receipt id the owner read the outcome from.
- Emits `pending_resolved`.
- Trust cost, stated in the README: a wrong `paid` can double-pay or block **one** claim; it
  can't touch any other allocation. The callback is built so this should never be needed:
  static reserved gas, no result bytes read, no branch that can panic.

Storage, per campaign (create app):

- `prepay_deposit({ account_id? })`, payable. Credits the attached NEAR to the sender's free
  pre-pay (default: the caller) and returns the new free balance as `"<u128>"` yocto.
- `prepay_balance_of({ account_id })` returns the free pre-pay as `"<u128>"` (`"0"` if none).
- `prepay_withdraw({ amount? })` transfers the caller's free pre-pay (all of it by default) to
  the caller.
- At creation, `ft_on_transfer` debits from the free pre-pay `campaign_bytes_cost`
  (**spent**: the campaign entry stays stored) plus `leaf_count × per_claim_storage` (reserved
  into `campaign.storage_reserved`), where
  `per_claim_storage = ft_storage_deposit + claim_entry_cost`. `leaf_count == 0` → `E108`.
  Too little free pre-pay → `E128` (refunded).
- Each claim draws `per_claim_storage` from **its own campaign's** reservation. One campaign
  never spends another's.
- `reclaim` releases the unused reservation back to the sender's free pre-pay. With
  `balance == 0` but a reservation left, it only releases the reservation (no transfer);
  `E118` only when both are 0.
- `fund_campaign_storage({ campaign_id })`, payable, anyone. It tops up a reservation when
  `leaf_count` was understated. After the deadline → `E125`; zero deposit → `E109`.
- `prepay_withdraw`: amount > free → `E128`; amount 0 → `E109`.
- `get_campaign` also returns `storage_reserved`.
- Each sender has a per-sender list of campaign ids, appended in `ft_on_transfer` and read
  with `campaigns_of`. Its entry is part of the measured campaign cost and of the
  `campaign_bytes_cost` bound.
- `claim_entry_cost` is measured by the contract (storage bytes of one claim entry ×
  storage price) and exposed with `ft_storage_deposit` by `storage_costs({ token_id })` →
  `{ ft_storage_deposit, claim_entry_cost, per_claim_storage, campaign_bytes_cost }`.
  `campaign_bytes_cost` is an **upper bound**: a campaign entry whose snapshot holds every
  current owner key. The real snapshot is a subset, so creation spends at most this, and the
  rest stays in the free pre-pay (withdrawable).
- The create app deposits only the shortfall:
  `campaign_bytes_cost + leaf_count × per_claim_storage − prepay_balance_of(sender)`.
- `get_config()` → `{ network, min_lifetime_ns, agent_ttl_ns, token_ids, storage_byte_cost }` (`storage_byte_cost` = `env::storage_byte_cost()`, yocto per byte; the create app adds one owner key's slack, 32 × this, to its shortfall), so the create form
  can refuse a too-early deadline before sending.
- `refresh_token_storage({ token_id })`, owner only. Reads the token's
  `storage_balance_bounds().min` into `ft_storage_deposit`. Until it has run for a token,
  `ft_on_transfer` from that token is refused with `E126_UNKNOWN_TOKEN`.
- Names avoid NEP-145's `storage_*`, because the return shapes differ.

`new` is private (`predecessor == current_account_id`, else `E107`). Deploy and `new` happen in **one batched transaction**, so nobody can
initialise the contract first.

Owner keys live in their own set, separate from attested agents, so building a campaign
snapshot never scans re-registered TEE agents.

`resolve_pending` on an entry that is not pending → `E108_INVALID_INPUT`.

**Deadline boundary:** `claim` iff `now <= deadline_ns`; `reclaim` iff `now > deadline_ns`.

**`claim` check order.** It is fixed so that input hitting two conditions has one expected code:

1. `E110_UNKNOWN_CAMPAIGN`
2. `E108_INVALID_INPUT` (hex/length, proof > 20, `expires_at_ns` beyond 1 h)
3. `E109_INVALID_AMOUNT`
4. `E125_CAMPAIGN_ENDED`
5. `E114_CLAIM_EXPIRED`
6. `E105_ALREADY_CLAIMED` / `E123_CLAIM_PENDING`
7. `E102_INVALID_MERKLE_PROOF`
8. `E101_INVALID_SIGNATURE` (policy, then ed25519)
9. `E129_INSUFFICIENT_BALANCE`
10. `E128_INSUFFICIENT_STORAGE` (`campaign.storage_reserved < per_claim_storage`)
11. `E130_INSUFFICIENT_GAS` (prepaid gas < `required_claim_gas()`)

Only after all of them pass does the claim proceed:

1. The claim becomes `pending` and the amount moves to in-flight.
2. `per_claim_storage` is debited from the campaign's reservation; the claim entry's bytes are paid from it.
3. The contract **always** calls
   `token.storage_deposit({ account_id: destination, registration_only: true })` with exactly
   `ft_storage_deposit` attached. There is no registration check: that would need an
   async view.
4. It then calls `ft_transfer`, with a `#[private]` callback on reserved gas.

There is **no credit-back** of NEP-145 refunds: the callback can't observe them, because
they arrive as a separate transfer and `storage_deposit` returns the same `StorageBalance`
either way. The sender is charged `ft_storage_deposit` (USDC: 0.00125 NEAR) per claim, and
any refund for an already-registered destination accrues to the contract.

The callback decides success from the **`ft_transfer` result only**. On NEAR a `.then` runs
even when an earlier receipt failed. For an **unregistered** destination, a failed
`storage_deposit` therefore shows up as a failed `ft_transfer`. For an already-registered
destination, `ft_transfer` can still succeed, and that is a correct payout.

**Attempt identity.** `on_claim` receives the attempt's `started_ns` and settles only if the
entry is still `Pending { started_ns }` with that same value; otherwise it does nothing.
This stops a late callback from an earlier attempt (one already settled by `resolve_pending`)
from settling a newer attempt for the same commitment.

On failure (callback or `resolve_pending(paid: false)`), the claim returns to `unclaimed`
and the amount moves from in-flight back to balance. Of that attempt's `per_claim_storage`,
`claim_entry_cost` is credited back to the campaign reservation, because the entry is removed
and its bytes are freed. The `ft_storage_deposit` part is **not** credited back: if
`storage_deposit` succeeded, that NEAR is gone. Repeated failures for one recipient therefore
cost the campaign `ft_storage_deposit` each.

Other notes:

- `per_claim_storage` is evaluated at claim time from the current `ft_storage_deposit`. A
  `refresh_token_storage` that raises the token minimum can leave a fully reserved campaign
  short for its last claims (`E128` → `fund_campaign_storage`).
- Pending → Claimed shrinks the entry; the freed bytes stay with the contract.
- `required_claim_gas()` is set from a sandbox measurement. An integration test submits a
  claim with exactly that gas.

The contract cannot check that a deposit equals the sum of leaves. The create app sends the
exact sum; an underfunded campaign fails later claims with `E129`.

## Views

```
get_network() -> "testnet" | "mainnet"
get_campaign({ campaign_id }) -> { sender, token, amount, merkle_root, deadline_ns,
                                   balance, in_flight, policy, snapshot: ["<hex32>"],
                                   storage_reserved } | null
claim_state({ campaign_id, commitment }) -> "unclaimed" | "pending" | "claimed"
campaigns_of({ sender, from_index?: u32, limit?: u32 }) -> ["<u64>"]   // creation order; limit default 50, max 100
get_agent({ account_id }) -> { kind: "owner" | "attested", measurement_id?, valid_until_ns } | null
required_claim_gas() -> "<u64>"      // the relayer attaches at least this; the contract owns the number
```

The verifier reads `merkle_root`, `deadline_ns` and the policy from `get_campaign` and
`get_network`, never from the request. It verifies the merkle proof for
`(commitment, amount)` and refuses to sign anything that is not in the tree.

## Events (NEP-297)

The contract logs `EVENT_JSON:{"standard":"zarf-near","version":"1.0.0","event":<name>,"data":[<obj>]}`:

| event | data |
| --- | --- |
| `campaign_created` | `campaign_id, sender, token, amount, merkle_root, deadline_ns, policy` |
| `claim_started` | `campaign_id, commitment, amount, destination, signer` |
| `claim_paid` | `campaign_id, commitment, amount, destination` |
| `claim_reverted` | `campaign_id, commitment, amount, destination, code: "E115_TOKEN_TRANSFER_FAILED"` |
| `reclaimed` | `campaign_id, amount` |
| `pending_resolved` | `campaign_id, commitment, amount, paid, evidence` |
| `reclaim_reverted` | `campaign_id, amount, code: "E115_TOKEN_TRANSFER_FAILED"` |

The create app takes `campaign_id` from `campaign_created`.

## Off-chain interfaces

**Leaf list** (published by the create app, T7). It is fetched by the claim app from
`<PUBLIC_LEAVES_URL>/<campaign_id>.json`:

```json
{ "campaign_id": "<u64>", "merkle_root": "<hex32>",
  "leaves": [ { "commitment": "<hex32>", "amount": "<u128>" } ] }
```

- Leaves are in tree order.
- The claim app recomputes the root and refuses the file if it differs from `get_campaign`.
- Emails and salts never appear in it.

**Relayer** (T5). `POST /claim` takes exactly the verifier's 200 body (the contract's `claim`
args) and refuses anything else. The transaction's final status can't tell a payout from a
revert, because `on_claim` returns `()` either way. The relayer therefore decides from the
NEP-297 events in the receipt logs:

| Events | HTTP | Body |
| --- | --- | --- |
| `claim_paid` | 200 | `{ "tx_hash", "status": "paid" }` |
| `claim_reverted` | 409 | `{ "error": "E115_TOKEN_TRANSFER_FAILED", "tx_hash" }` |
| neither, or a timeout | 202 | `{ "tx_hash", "status": "submitted" }` |

The claim app trusts 200 `paid` and 409 `E115`: both come from our contract's events in the
executed receipt. On 202 it polls `claim_state` at `optimistic` finality, and treats
`unclaimed` as final only after `pending` was seen or after a 20 s grace.

## Verifier errors (HTTP)

Order: input shape → token → chain views → E110 → E125 → E105/E123 → COMMITMENT_MISMATCH →
E102 → E101 → E129 → sign. Nothing is signed on any error.

| Code | HTTP | When |
| --- | --- | --- |
| `NOT_FOUND` | 404 | any route except `/claim`; any method except POST/OPTIONS |
| `E108_INVALID_INPUT` | 400 | body not a JSON object; field missing; bad u64/hex32; proof not ≤ 20 lowercase hex32 |
| `BAD_DESTINATION` | 400 | destination is not a valid AccountId (checked before any token work) |
| `E109_INVALID_AMOUNT` | 400 | amount 0, not decimal, or ≥ 2^128 |
| `MALFORMED`, `BAD_ALG`, `UNKNOWN_KID`, `BAD_SIGNATURE`, `BAD_ISSUER`, `BAD_AUDIENCE`, `EXPIRED`, `EMAIL_NOT_VERIFIED`, `NO_EMAIL`, `BAD_EMAIL`, `BAD_NONCE` | 401 | Google id_token checks |
| `E110_UNKNOWN_CAMPAIGN` | 404 | no such campaign |
| `E125_CAMPAIGN_ENDED` | 409 | now > deadline_ns |
| `E105_ALREADY_CLAIMED`, `E123_CLAIM_PENDING` | 409 | from `claim_state` |
| `COMMITMENT_MISMATCH` | 403 | HMAC(salt, email) ≠ commitment (wrong account or wrong link) |
| `E102_INVALID_MERKLE_PROOF` | 403 | (commitment, amount) not in the tree |
| `E101_INVALID_SIGNATURE` | 403 | our signer (or measurement) is not in the campaign snapshot, or `get_agent(our signer)` is null or expires before `expires_at_ns` |
| `E129_INSUFFICIENT_BALANCE` | 409 | balance < amount |
| `VERIFIER_MISCONFIGURED` | 500 | SIGNER_SEED, CONTRACT_ID or GOOGLE_CLIENT_ID unset |
| `UPSTREAM_UNAVAILABLE` | 503 | Google JWKS or a chain read failed |

200 returns `{ campaign_id, commitment, amount, proof, destination, expires_at_ns, signer, signature }`.
In both modes the verifier checks its own `get_agent`: it is refused while a key is removed,
for example in the window of a remove + add extension.

## Errors

Panic messages start with a stable code. The numbers reuse Zarf's Stellar vesting codes
where the name matches; everything else is new.

| Code | When |
| --- | --- |
| `E101_INVALID_SIGNATURE` | signer not allowed by the campaign policy, or ed25519 fails |
| `E102_INVALID_MERKLE_PROOF` | proof does not reach the campaign root |
| `E105_ALREADY_CLAIMED` | commitment already paid |
| `E107_UNAUTHORIZED` | caller lacks the role (owner, sender, token, private callback) |
| `E108_INVALID_INPUT` | malformed hex/length/AccountId, proof > 20, `expires_at_ns` beyond 1 h, bad `msg` |
| `E109_INVALID_AMOUNT` | amount 0 or overflow |
| `E110_UNKNOWN_CAMPAIGN` | no such campaign id |
| `E114_CLAIM_EXPIRED` | `expires_at_ns < now` |
| `E115_TOKEN_TRANSFER_FAILED` | an `ft_transfer` failed; state restored (event, not panic) |
| `E117_NOT_YET_RECLAIMABLE` | reclaim while `now <= deadline_ns` |
| `E118_NOTHING_TO_RECLAIM` | balance (excluding in-flight) is 0 |
| `E119_INVALID_DEADLINE` | `deadline_ns < now + min_lifetime_ns` |
| `E123_CLAIM_PENDING` | commitment has a transfer in flight |
| `E125_CAMPAIGN_ENDED` | claim while `now > deadline_ns` |
| `E126_UNKNOWN_TOKEN` | `ft_on_transfer` from a token not on the allow-list |
| `E127_NO_VERIFIER` | the policy snapshot would be empty |
| `E128_INSUFFICIENT_STORAGE` | free pre-pay too low at creation, or the campaign reservation too low at claim |
| `E129_INSUFFICIENT_BALANCE` | campaign balance < amount |
| `E130_INSUFFICIENT_GAS` | prepaid gas below what the transfer + callback need (checked before `pending`) |
| `E132_DUPLICATE_CAMPAIGN` | `ft_on_transfer` from a sender that already has a campaign with this `merkle_root` |
| `E131_INVALID_ATTESTATION` | `register_agent` quote/measurement/ppid check fails |

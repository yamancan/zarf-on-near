# Claim format (v1)

Every layer — `contract/` (Rust), `verifier/` and `web/` (TypeScript) — must agree on
these bytes exactly. `spec/vectors.json` is generated by `spec/gen-vectors.mjs` and is
the acceptance test: each layer's test suite loads it and must reproduce every value.
Change this file only together with the generator, and regenerate.

Owner: orchestrator (`zarf main`). Other sessions propose changes; they don't edit.

## Encodings

- Bytes in JSON: lowercase hex, no `0x`. Signatures and keys too.
- `u64` / `u128` in JSON: decimal strings (NEAR `U64`/`U128` convention; ns timestamps exceed 2^53).
- Integers inside hashed or signed bytes: little-endian, fixed width.
- Strings inside hashed or signed bytes: UTF-8, prefixed by a 1-byte length (account ids are ≤ 64 bytes).
- All times are **nanoseconds** (`env::block_timestamp()`), named `*_ns`.

## Email and commitment

```
canonical_email = lowercase(trim(email))          // no dot/plus folding, no domain remap
campaign_salt   = 32 random bytes, one per campaign
commitment      = HMAC-SHA256(key = campaign_salt, msg = utf8(canonical_email))   // 32 bytes
```

The sender's CSV must contain the address Google returns in the id_token `email` claim.

## Merkle tree

```
leaf = sha256(0x00 || commitment[32] || amount_u128_le[16])
node = sha256(0x01 || min(a, b) || max(a, b))      // byte-wise lexicographic order
```

- Build bottom-up over leaves in CSV order. On a level with an odd count the last node is
  **carried up unchanged** (never duplicated).
- One leaf: `root = leaf`.
- `proof` = sibling hashes from leaf to root, skipping levels where the node was carried up.
- Verify: `h = leaf; for s in proof: h = node(h, s); h == root`.
- Contract limit: `proof.len() <= 20` (≈1M leaves), else `E108_INVALID_INPUT`.
- `amount == 0` is refused (`E109_INVALID_AMOUNT`) at create (no such leaf should exist) and claim.

The 0x00/0x01 prefixes keep a leaf from being presented as an internal node.

## Verifier keys

The verifier has two keys, both registered on the contract by `set_verifier`:

- `verifier_pubkey`: ed25519 (32 bytes), signs claims.
- `seal_pubkey`: X25519 (32 bytes), receives sealed campaign salts.

The create app reads `seal_pubkey` from the contract view, never from anywhere else.

## Sealed salt

```
eph            = fresh X25519 keypair
shared         = X25519(eph.priv, seal_pubkey)
key            = HKDF-SHA256(ikm = shared, salt = eph.pub || seal_pubkey, info = "ZARF-NEAR-SALT-V1", len = 32)
iv             = 12 random bytes
ct || tag      = AES-256-GCM(key, iv, plaintext = campaign_salt, aad = merkle_root)
sealed_salt    = eph.pub[32] || iv[12] || ct[32] || tag[16]       // 92 bytes, hex in JSON
```

`aad = merkle_root` stops a sealed salt from being reused against another tree.

## Nonce (Google `nonce` claim)

```
nonce = lowercase_hex(sha256(utf8(destination)))     // 64 chars
```

`destination` is the NEAR account the contract pays: the recipient's account or the 1Click
deposit address. It is chosen **before** the Google redirect.

## Signed claim payload

```
payload =
    "ZARF-NEAR-CLAIM-V1"                  // 18 ASCII bytes, domain tag
 || u8 len || utf8(network)               // "testnet" | "mainnet"
 || u8 len || utf8(contract_id)
 || u64_le(campaign_id)
 || commitment[32]
 || u128_le(amount)
 || u8 len || utf8(destination)
 || u64_le(expires_at_ns)
signature = ed25519_sign(verifier_priv, payload)         // over the raw payload bytes
```

The contract rebuilds `payload` from its own `network`/`current_account_id` and the call
args, then `env::ed25519_verify(signature, payload, campaign.verifier_pubkey)`.
The verifier sets `expires_at_ns = now + 10 min`. The contract refuses
`expires_at_ns < now` (`E114_CLAIM_EXPIRED`) and `expires_at_ns > now + 1 h`
(`E108_INVALID_INPUT`), so a signature cannot be made long-lived.

## Contract calls (JSON args)

`ft_on_transfer(sender_id, amount, msg)` where `msg` is

```json
{ "merkle_root": "<hex32>", "deadline_ns": "<u64>", "sealed_salt": "<hex92>" }
```

`claim` args:

```json
{ "campaign_id": "<u64>", "commitment": "<hex32>", "amount": "<u128>", "proof": ["<hex32>"],
  "destination": "<account_id>", "expires_at_ns": "<u64>", "signature": "<hex64>" }
```

`set_verifier`: `{ "verifier_pubkey": "<hex32>", "seal_pubkey": "<hex32>", "code_hash": "<hex32>|null" }`

The contract cannot check that a deposit equals the sum of leaves; the create app sends the
exact sum. An underfunded campaign fails later claims with `E129_INSUFFICIENT_BALANCE`.

## Errors

Panic messages start with a stable code; numbers follow Zarf's vesting contract where the
meaning matches (`contracts/soroban/zarf/vesting/src/lib.rs:106-127` in the Stellar repo).

| Code | When |
| --- | --- |
| `E101_INVALID_SIGNATURE` | ed25519 check fails |
| `E102_INVALID_MERKLE_PROOF` | proof does not reach the campaign root |
| `E105_ALREADY_CLAIMED` | commitment already paid |
| `E107_UNAUTHORIZED` | caller lacks the role (owner, sender, token) |
| `E108_INVALID_INPUT` | malformed hex/length, proof > 20, `expires_at_ns` beyond 1 h |
| `E109_INVALID_AMOUNT` | amount 0 or overflow |
| `E110_UNKNOWN_CAMPAIGN` | no such campaign id |
| `E114_CLAIM_EXPIRED` | `expires_at_ns < now` |
| `E115_TOKEN_TRANSFER_FAILED` | `ft_transfer` failed; claim returned to unclaimed (emitted as an event, not a panic) |
| `E117_NOT_YET_RECLAIMABLE` | reclaim before deadline |
| `E118_NOTHING_TO_RECLAIM` | balance (excluding in-flight) is 0 |
| `E119_INVALID_DEADLINE` | `deadline_ns < now + MIN_LIFETIME` |
| `E123_CLAIM_PENDING` | commitment has a transfer in flight |
| `E125_CAMPAIGN_ENDED` | claim after deadline |
| `E126_UNKNOWN_TOKEN` | `ft_on_transfer` from a token not on the allow-list |
| `E127_NO_VERIFIER` | campaign created before `set_verifier` |
| `E128_INSUFFICIENT_STORAGE` | sender's storage pre-pay too low |
| `E129_INSUFFICIENT_BALANCE` | campaign balance < amount |
